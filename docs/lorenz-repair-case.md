## 修复过程暴露并解决的工作台问题

第一次模型尝试反复读文件并耗尽预算。ACI 原本把读文件结果限制在 4000 字符，
模型客户端又将其压缩到末尾 800 字符，导入语句经常丢失。
现在保留已有边界内的读文件 / 搜索结果，明确提示截断及分段读取方法，
并在首个观测中提供本次授权的副作用动作。新增回归测试覆盖该问题。

随后一次尝试在 GitHub TLS 握手阶段失败，未调用模型；源码缓存辅助脚本也曾因空目录
已存在而退出。均保留为失败，不计入成功。最终修复与复跑使用此前真实下载、检查为
干净且提交号相符的 Git 缓存，依赖使用预装科学计算基础镜像，不能称为冷启动测速。

历史数值验收记录的 `code_under_test` 曾沿用 v1.7.5 的静态描述；实际运行计划、Git
提交、冻结清单和源码哈希均为上述 v1.7。已经修正产品规则描述，改为引用实际冻结
提交；原始历史记录保留，证据快照与交接来源说明明确列出这项文字更正。

## 如何重新运行真实模型修复

先准备项目 Python 环境和 Docker 基础镜像，配置现有模型环境变量，再执行：

```powershell
python scripts/accept_repair.py
# 如配置保存在本机 .env，仅加载三个模型设置；不会打印密钥或执行其中的命令。
python scripts/accept_repair.py --env-file .env
```

脚本先跑零修复基线，确认出现目标源码错误，再创建新的模型修复任务。
最终必须同时通过当前独立验收、干净复跑、下载包 SHA-256 校验。
模型动作通过现有 PaperACI 执行，不能以模型声称完成代替真实重验。

网络不稳定时可明确使用已存在的干净源代码缓存，而不是伪装远端下载成功：

```powershell
python scripts/accept_repair.py --baseline-run <已保存的基线运行ID> `
  --source-cache <干净的固定提交检出目录>
```

`--source-cache` 检查 Git 提交、origin 和工作区无修改；不改变通用服务禁止本地仓库
输入的边界。该选项仅用于维护者在本机运行这个验收脚本。

## 交给 Windows 队友的材料

`scripts/build_repair_handoff.py` 为已通过验收的运行创建独立交接目录和 ZIP：

- 原始上游源码快照、许可证、提交来源说明。
- 实际原始报错、模型决策、只含 AI 源码修改的 diff。
- 已校验的修复材料包、精确依赖列表、独立验收器。
- 固定 Linux amd64 环境镜像、来源与 SHA-256。
- 不需要模型密钥的 `replay.py` 和 Windows 步骤说明。

镜像可以从相同运行容器捕获，但打包前必须确认其 `pip freeze` 与成功运行完全一致。
镜像不含挂载的科研工作区；队友会重新计算系数。交接使用固定环境，不是独立冷装依赖。

队友在已启动 Docker Desktop（Linux containers / WSL2）的 Windows x64 电脑上，
完整解压 ZIP，使用 Python 3.11+ 执行：

```powershell
python replay.py --participant 队友
```

脚本核对材料、导入镜像，在新容器重现原始报错，再应用冻结补丁，在另一个新容器运行，
最后用没有源码挂载的断网只读容器独立验收。不会复制发送者的系数或实验元数据。
本地自检必须传 `--role local-check`，不得冒充队友验收。

队友需回传新生成的 `receiver-*/feedback.json`；失败时同时回传 `*.err`。
另外请本人说明：是否独立电脑、是否需要指导、环境准备耗时、哪里卡住。
在收到其实际运行结果与确认之前，跨机器交接状态始终是 **pending**。
