# 科研代码复现工作台：需求与开发设计评审稿

- 版本：v0.2 路线图草案，含 8.5 天预览版冲刺排期
- 日期：2026-11-21
- 时间约束：8.5 天，代码由 AI 编写；本轮交付范围与逐日安排以第 12.1–12.7 节为准
- 状态：待评审；本文不代表功能已经实现，也不授权部署或修改现有代码
- 基线：当前 `feat/run-guidance` 工作区，包含未提交改动；不是远程 main，也不是前端 PR 链的最终状态
- 建议交付形态：本地部署、单用户工作台，先做小规模受支持任务，不直接开放公共多租户服务

## 1. 先看结论

### 1.1 产品定位

给一个科研代码仓库，先说明运行条件和验证范围，再在受限环境里试跑、修复、复验，最后交付一份可检查的结果，以及重新运行所需的材料。

不是再做一个通用编程 Agent，也不承诺输入任意论文就能复现全部实验。

核心分工：

| 部分 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 编程 Agent / 当前模型适配层 | 看报错、提出修复动作 | 自己修改成功标准、决定无限重试、宣布科研结论成立 |
| Harness | 编排、执行边界、预算、状态、终止与清理 | 把所有错误都当作模型可以解决的问题 |
| 验证器 | 按事先确定的规则检查退出状态、产物和指标 | 相信模型的“已经修好”或仅凭日志文字判成功 |
| 用户界面 | 解释条件、进展、证据与下一步 | 用动画代替真实事件，用绿色状态掩盖验证缺失 |

### 1.2 本轮建议优先做的三件事

1. **先能上手**：贴链接后给出可理解的运行体检单，缺什么、将运行什么、最多尝试多久，一次说清楚。
2. **再能信任**：区分“程序跑通”“产物合格”“达到指定指标”，修复后在干净环境复跑，不把退出码 0 包装成论文复现成功。
3. **最后证明值得用**：用冻结的真实任务集，对比当前版本、通用 Agent 和升级版本，公开成功率、误报、时间与成本。

### 1.3 首版边界

| 纳入 v0.2 | 暂不纳入 |
| --- | --- |
| 公开 HTTPS Git 仓库，固定到具体 commit | 私有仓库凭据管理、任意远程文件或网页作为执行入口 |
| CPU、单机、Python 小型科研任务 | GPU 调度、分布式训练、长时间大模型训练 |
| 受维护的运行/验收任务配置 | 自动从任意论文准确提取所有实验条件 |
| 现有 requirements 安装能力及明确支持的依赖组合 | 自动支持所有 Poetry、Conda、系统包、编译工具链 |
| 受控修复、独立验收、干净环境复跑 | 多 Agent 组织、开放插件市场、任意宿主命令 |
| 本地单用户运行与材料导出 | 公共 SaaS、多租户配额、团队权限、计费 |

支持范围是主动选择，不是宣称范围外项目一定不能运行；范围外项目可以得到明确的“当前不支持/需要补充条件”，不能被归类为“论文不可复现”。

### 1.4 本次 8.5 天交付与完整路线图的区别

本轮不是全量 v0.2：优先在少量受维护 CPU 任务上做真实的体检确认、运行修复、独立指标验证和干净复跑，同时让四个用户视图明显改善。通用仓库预检、通用材料导出、20 任务对照等保留为后续需求；未通过门槛的指标/复跑能力明确延期，不能只改名称就当作完成。

第 3–11、13 节描述完整设计，具体落地仅限第 12 节列出的子集，不要求 8.5 天内实现全部接口、模型与异常类型；已有安全约束以及本轮开放能力涉及的可信性约束仍然适用。第 14 节的大样本对照与正式版门槛不是本轮承诺，本轮按第 12.5–12.6 节验收。

## 2. 用户与要解决的问题

### 2.1 核心用户

- 想试用论文开源实现，但不熟悉依赖和环境的学生、研究人员。
- 想快速判断一个开源实现是否具备实验条件的工程人员。
- 想给科研仓库做回归检查的维护者；批量使用不是第一阶段必需功能。

### 2.2 典型任务

用户拿到一个算法仓库，想先验证一个小型示例，而不是立刻完整训练整个模型。

期望流程：

1. 粘贴仓库链接；可选填写 revision 或选择已维护的示例任务。
2. 看到系统识别的 Python、依赖、数据、硬件要求及其来源。
3. 确认执行命令、验证标准、运行预算和自动修复开关。
4. 不需要理解 ACI 等内部术语，也能知道当前在做什么。
5. 成功时拿到证据、修改和复跑材料；失败时知道卡在哪里、下一步可以做什么。

### 2.3 不应出现的体验

- 没确认就开始下载大数据或长时间训练。
- 缺私有数据，却让模型连续修改代码试图“修好”。
- 用户只看到一个红色失败，没有失败阶段、证据和建议。
- 运行退出正常，界面就写“已验证论文结论”。
- 修复时改坏验收脚本、降低阈值，系统反而显示成功。
- 看似有报告，换个新环境却无法重跑。

## 3. 结果语义：先定义什么叫成功

### 3.1 三个相互独立的维度

不能只用一个 `verified: true` 表达全部事实。

| 维度 | 建议值 | 说明 |
| --- | --- | --- |
| 工作流状态 `state` | queued / preparing / planning / installing / testing / diagnosing / repairing / verifying / replaying / succeeded / failed / cancelled | 系统当前走到哪一步 |
| 验证等级 `verification.level` | none / execution / artifact / target | 实际完成了哪一级检查 |
| 干净复跑状态 `replay.status` | not_requested / pending / running / passed / failed / blocked | 同一方案能否在新的干净环境通过相同验收 |

`verification.status` 另取 `not_run / passed / failed / blocked`；等级说明检查种类，状态说明结果，不能把“尝试过 target 检查”当成“达到 target”。

现有 `outcome` 表达成功、失败、不可修复、预算等结束原因，保留它与验证证据的区别；迁移时后端、前端、事件解析和测试统一更新，不新增一套长期并存的“旧成功/新成功”逻辑。

### 3.2 验证等级定义

| 等级 | 必须满足的判据 | 用户文案 |
| --- | --- | --- |
| execution | 指定命令执行结束，退出码 0，未超时 | 程序运行通过；尚未验证科研结果 |
| artifact | execution 通过，且指定产物属于本次运行、路径合法、结构/类型/必需字段通过规则校验 | 产物检查通过 |
| target | artifact 通过，可信验证器检查任务规定的指标、数据条件和阈值通过 | 指定任务指标达标 |

没有配置指标规则，就不能出现“指标达标”。

即使达到 target，也只代表指定版本、数据与运行配置下的指定任务通过，不等于整篇论文的结论得到验证，更不等于独立科学审查。

### 3.3 干净复跑与最终标题

- 正式验证任务默认要求一次干净复跑，先运行、再修复、再复跑的开销必须算入预算。
- 若当前环境通过、干净复跑失败，标题为“当前运行通过，干净复跑失败”，不得显示完整成功。
- 若网络或数据来源不可用导致无法复跑，显示“当前运行通过，复跑条件不足”，不能断言修复无效。
- 用户选择探索试跑、未要求干净复跑时，显示“试跑通过，未验证可复跑性”。
- 两次验证使用相同验证规则与哈希、数据版本、指标计算方式和种子约定。
- 不确定性必须留在结论中，模型不能把 `unknown` 改成肯定结论。

### 3.4 终态组合与旧字段派生

`verified` 始终等于当前环境的 `verification.status == passed`，不因后续复跑失败或取消而抹去已经取得的证据；页面不得仅凭该布尔值显示完整成功。

| 当前验收 | 复跑/结束原因 | state | outcome | verified | 顶部结论 |
| --- | --- | --- | --- | --- | --- |
| passed | 正式任务复跑 passed | succeeded | succeeded | true | 指定等级通过，干净复跑通过 |
| passed | 探索试跑，事先确认 not_requested | succeeded | succeeded | true | 试跑通过，未验证可复跑性 |
| passed | 复跑验证 failed | failed | failed | true | 当前运行通过，干净复跑失败 |
| passed | 复跑缺数据/依赖源等条件 blocked | failed | failed | true | 当前运行通过，复跑条件不足 |
| failed / not_run / blocked | 普通执行、产物或验收器错误 | failed | failed | false | 展示实际失败阶段；验收器故障不得归因于仓库 |
| failed / not_run / blocked | 明确不可修复或当前不具备条件 | failed | unrepairable | false | 当前任务条件不足或超出支持范围，不评价论文真实性 |
| 任意 | 总预算耗尽 | failed | budget_exceeded | 按当前验收派生 | 预算已用完，同时保留已通过检查 |
| 任意 | 用户取消 | cancelled | cancelled | 按当前验收派生 | 已取消，同时保留已有证据 |

复跑尚未结束时保持 replaying，不提前写 succeeded。复跑阶段被取消或耗尽预算时，`replay.status=blocked`，另记录 `reason=cancelled/budget_exceeded`；未开始的复跑记录 `blocked` 及 `reason=not_started_before_termination`，不得把不完整任务改成 not_requested。

正式任务必须要求复跑；缺 profile 或主动不复跑只能走事先明确确认的探索试跑。误报按“验证等级”和“完整可复跑成功”分别统计，合法的“指标已达标，但复跑未完成”不是指标误报。

## 5. 用户流程与页面需求

### 5.1 入口页

默认只展示：

- 仓库 URL 输入框。
- “检查运行条件”按钮。
- “没有仓库？试一个示例”入口，第一项选择可快速运行的小任务。

高级设置折叠：revision、显式执行命令、Python 版本、产物、任务配置、预算。

折叠区域必须不可被 Tab 聚焦，不能发生隐藏按钮误启动运行。

### 5.2 预检页

分四块显示：

| 区块 | 展示内容 |
| --- | --- |
| 检查对象 | 仓库、固定 commit、检查时间、所选任务 |
| 运行条件 | Python、CPU/GPU、依赖清单、数据来源与可用性 |
| 执行与验收 | 将执行的命令、预期产物、验证等级、阈值来源 |
| 开销与提醒 | 时间上限、最大修复轮数、模型调用预算、网络说明 |

每条判断需要 `status`、`source`、`evidence` 和建议动作，状态取 `satisfied / missing / unsupported / unknown`。

规则命中和模型推测必须区分：例如“任务配置要求 GPU”为明确证据，“README 提到 CUDA，可能需要 GPU”为待确认线索。

预检阶段允许受限克隆和静态读取，不安装依赖、不执行仓库脚本、不导入仓库 Python 模块、不运行模型建议的探测命令。

### 5.3 预检分流

- `ready`：必要条件明确满足，可确认运行。
- `needs_input`：缺命令、任务选择等可补信息，展示相应表单。
- `unsupported`：已知需要当前不支持的 GPU、私有凭据或依赖系统，解释边界。
- `unknown`：静态证据不足；用户可明确选择探索试跑，但降低承诺，不允许绕过安全检查。

安全拒绝不属于 `unknown`，例如仓库地址指向内网，不能提供“仍然运行”按钮。

### 5.4 确认运行

确认卡必须包含：

- 固定 commit 与运行计划摘要。
- 本次验证目标和不验证的内容。
- 自动修复开关、允许修改的范围、最大轮数。
- 总时间上限、单步上限、模型调用上限。
- 是否要求干净复跑。
- 哪些仓库片段和日志可能发送给配置的模型服务。

没有可靠价格配置时，只显示时间、调用次数和 token 上限，费用显示“未知”，不能编造金额。

重复点击或网络重试只创建一个任务；服务端以幂等键和请求摘要校验，不能仅依赖按钮变灰。

### 5.5 运行页

默认回答三个问题：当前在做什么、已经得到什么结果、用户是否需要处理什么。

主流程建议为：

```text
拉取与计划 → 安装依赖 → 运行任务 → 验证结果 → 干净复跑 → 结果
                 │          │          │
                 └────可修复失败───────┘
                            ↓
                      诊断 → 受控修复
                            ↓
                   重跑对应执行阶段并复验
```

- 图是状态和事件的展示，不是五个独立 Agent 的展示。
- 安装失败修完重跑安装；测试或可修复产物/指标失败，修完重跑任务后重新验证。
- 判定条件不足、不可修复或预算耗尽时，走结束分支，不虚构修复回环。
- 干净复跑失败在 v0.2 直接形成不完整结果，不自动新增第二套修复循环。
- 默认展示最近三条关键进展；动作参数、ACI 拦截、容器与详细日志进入详情。
- 不展示伪精确百分比；只展示真实阶段、已用时间、预算剩余和真实次数。
- 终态保留结果，不自动返回首页；取消按钮可用，并展示清理是否完成。
- 轮询断网后提示重连；恢复后从事件游标续接，终态事件和最终结果均获取完成才停止刷新。

### 5.6 结果页

首屏按固定顺序展示：

1. 结论及验证范围。
2. 原始失败是什么，或者原仓库已通过。
3. 修改了什么：代码、依赖、允许的环境变量分别列出。
4. 哪些检查通过/失败/未执行，以及证据链接。
5. 干净复跑是否通过。
6. 下载报告、补丁、环境信息和复跑材料。
7. 可执行的下一步：补充条件后新建运行、查看失败步骤、复制运行配置。

补资料或更换计划必须创建带 `parent_run_id` 的新运行，不覆盖旧记录，不伪装成原运行无缝恢复。

## 6. 功能需求与验收

| ID | 需求 | 优先级 | 验收条件 |
| --- | --- | --- | --- |
| R01 | URL/revision 校验和受限预检 | P0 | 非法/内网地址被拒；静态预检不执行项目代码；返回固定 commit |
| R02 | 有证据的运行体检单 | P0 | 每条条件可查看来源；推测和确定事实可区分；缺失条件有下一步 |
| R03 | 确认与冻结运行计划 | P0 | 用户确认摘要与实际执行一致；修改计划后原确认失效 |
| R04 | 统一预算与取消 | P0 | 预检、运行有独立上限；运行的模型/安装/修复/验收/复跑共享总预算 |
| R05 | 结构化验证结果 | P0 | 区分 execution/artifact/target；缺规则不标指标通过 |
| R06 | 不可由修复动作修改的验收规则 | P0 | 改阈值、覆盖验证器或伪造日志不能让负例通过 |
| R07 | 干净环境复跑 | P0 | 新工作目录和新容器；只使用冻结输入及声明变更，执行同一验证 |
| R08 | 完整修复材料 | P0 | 正确包含允许范围内新增/修改/删除文件、依赖变化和允许环境变化 |
| R09 | 可理解的结论与证据 | P0 | 每项结论对应运行/验证证据，不依赖模型摘要才能解释 |
| R10 | 渐进式运行界面 | P0 | 新用户不看原始日志可完成一次任务；键盘操作覆盖主要流程 |
| R11 | 真实任务与 Agent 对照 | P0 | 冻结任务配置、预算、模型、原始结果和评测脚本，可重复统计 |
| R12 | 稳定单用户启动体验 | P0 | README 中一条已验证的启动入口或明确的最短步骤；缺 Docker/模型配置提示具体 |
| R13 | 多次随机种子/统计一致性 | P1 | 对随机算法可配置重复运行与指标容差，报告每次结果，不只报最好值 |
| R14 | 任务批量评测入口 | P1 | 复用单任务契约，结果隔离，支持串行批处理，不先引入分布式队列 |

P0 表示完整 v0.2 正式验收需要具备，不是 8.5 天冲刺的全量承诺，也不表示必须放在同一个 PR。本轮各需求的受限实现与延期部分见第 12.2 节；不能因一个小任务跑通就把 R01–R12 全部标为完成。预览版可以先交付易用性改善，但不能提前宣传尚未验证的复现能力。

## 7. 任务配置与证据模型

### 7.1 受维护的任务配置 `TaskProfile`

优先扩展现有 target manifest，不同时维护一套含义相同的 profile 配置。

| 字段 | 含义 |
| --- | --- |
| id / version | 任务标识与不可变版本 |
| repo_url / revision | 仓库与固定 commit |
| code_under_test | 实际被测对象：检出源码或发布包；发布包记录名称、版本和可取得的哈希，不能用仓库 commit 冒充包版本 |
| runtime | 已支持的 Python、平台和 CPU/内存需求 |
| command | 参数数组，不是拼接 shell 字符串 |
| dataset | 数据标识、来源、许可、版本/哈希与所需文件；未知项明确为空 |
| seed_policy | 固定随机种子或允许的随机性说明 |
| expected_artifacts | 路径、类型、大小上限和结构规则 |
| validator_ref / validator_digest | 服务端维护的验证器及内容哈希 |
| targets | 指标名称、单位、比较方法、阈值/容差及来源 |
| allowed_changes | 允许修改的路径、依赖和环境变量范围 |
| default_budget | 任务建议预算，仍受部署上限限制 |

受维护 profile 的科学指标和验证器由维护者审核；用户自填目标可以执行，但报告必须标注“用户自定义标准”，不能冒充已审核的论文标准。

### 7.2 预检记录 `PreflightResult`

保存：输入摘要、固定 commit、生成时间、有效期、条件检查列表、计划候选及来源、可选验证等级、阻塞项、确认摘要哈希。

预检不是完整可运行性证明：动态依赖、数据权限与训练时错误可能只有运行时才能发现，UI 和报告要明确此限制。

### 7.3 验证记录 `VerificationResult`

保存：规则版本/哈希、输入产物哈希、验证时间、等级、状态、每项检查、观测指标、目标指标、比较结果、证据引用、未验证事项。

仅接受严格 JSON 等已声明的安全数据格式；拒绝 NaN/Infinity、超限数值与文件、路径越界；不反序列化仓库产生的 pickle，不执行产物内脚本，不用 `eval` 解析指标。

指标优先由可信验证器根据原始输出重新计算；不能只读取日志中“accuracy=0.99”或模型自报的数字。

### 7.4 修复与复跑记录

`RepairManifest` 记录允许的文件变更及哈希、依赖状态、允许的环境变量和执行计划。

`ReplayResult` 记录新会话标识、原始 commit、修复材料摘要、镜像 digest、数据/依赖摘要、每项验证结果，以及不一致原因。

复跑与材料导出必须引用同一个冻结 RepairManifest 及哈希，不能复跑时读取完整工作区、下载时却只给一个被截断的补丁。

`bundle.integrity` 取 `complete / incomplete / blocked`，逐条记录应有内容、实际内容、未包含的原因，以及仅通过合法来源引用的外部输入。完整表示在声明的外部前提下复跑所需变更和配方完整，不表示压缩包离线包含所有代码、数据和镜像。

二进制变更以限大小的文件载荷和哈希表达，删除操作独立列出；必要但被 Git 忽略的文件须通过显式允许规则纳入，不能一概丢弃，也不能批量导出所有忽略文件。超限或不允许导出的必要内容会使清单不完整；截断补丁不得标记完整。

环境变量只导出明确允许且非敏感的值；模型 API key、代理凭据、宿主路径等不能进入下载材料。

## 8. 后端设计

### 8.1 原则

- 保留现有 FastAPI、worker、HarnessRunner、ACI、沙箱和文件存储结构，不为这次升级换框架。
- 不急于接入多个 Agent 框架；当前模型适配层先保留，mini-swe-agent 先作为独立对照。
- 当前 guidance 保持事件/结果的确定性解释职责；输入帮助与静态检查复用现有依赖校验、Agent 的目录/README 摘要能力，但需要独立的预检服务，不能直接调用会执行项目代码的逻辑。
- 真正访问仓库的受限预检作为有状态任务执行，避免长时间占住 API 请求；复用现有分层中文展示组件，不再搭建重复的运行监控页面。
- 验证规则、预算和终止条件由服务端决定，不能靠系统提示词约束模型。
- 每个业务能力必须有失败路径和对应前端文案。

### 8.2 预检执行

1. 校验 URL、revision、用户输入长度和受支持来源。
2. 在有限时间和大小内拉取固定版本；不初始化仓库要求的任意 submodule 或 LFS 下载。
3. 将预检工作目录视为不可信输入，限制文件读取大小、数量和软链接访问。
4. 读取支持的项目描述和依赖文件，匹配现有 target/profile。
5. guidance 输出规则建议；必要时模型补充计划候选，但明确标记来源，不执行候选命令。
6. 保存结构化预检结果和有效期，返回确认所需摘要。

预检草案建议有效期 30 分钟；正式运行创建时校验有效期和确认摘要，受理成功即冻结完整快照。排队等待期间过期不作废已受理的任务，开跑时核验冻结 commit 和材料完整性，不重新跟随分支 HEAD，也不重新向模型生成另一份计划；排队等待不计入执行预算，但单独记录等待时长。

补命令、修改 Python/数据选择/预算或过期重检，统一再次调用 `POST /api/preflights`，携带完整最新输入并创建新预检记录；不原地修改旧记录、不新增一套同义更新接口。静态结果可安全复用时由服务端优化，不能改变新记录的确认语义。

`confirmation_digest` 由服务端对规范化后的有效配置计算，并绑定以下内容：仓库与固定 commit、实际被测源码/包、profile 版本、命令参数数组、Python/镜像、数据版本、产物规则、验证器哈希和阈值、允许动作/修改范围、有效预算、是否复跑、运行模式，以及会发送给模型的数据范围。除排序和明确规定的规范化外，不得忽略影响执行或费用的字段。

创建正式运行只引用服务端保存的预检 ID 与摘要；客户端若同时提交影响执行的字段，必须与冻结配置一致，否则返回 `confirmation_mismatch`，不能用客户端自算摘要替换服务端记录。

探索试跑在预检中明确 `mode=exploratory`，并记录用户对未知条件的确认与 `require_clean_replay=false`；安全拒绝不允许转换为探索试跑。无预检的直接创建请求也必须显式声明探索模式及预算，只能获得试跑标签。

若排队后必需镜像、固定代码或数据实际不可获得，按执行条件不足结束并保留冻结计划，不静默选择其他版本；用户调整条件后新建预检/运行。

### 8.3 统一预算

建议新增明确的 `total_budget_seconds`，不要改变现有 `timeout_seconds` 的单步含义而不更新契约。

建议默认值，仅作为评审初值：

| 项目 | 建议值/规则 |
| --- | --- |
| 预检总时长 | 120 秒上限，与正式运行分开计量 |
| 正式运行总预算 | 默认 900 秒，部署可设更低上限 |
| 单个执行步骤 | 不超过用户单步设置与剩余总预算的较小值 |
| 修复轮数 | 默认沿用 3 轮；正式任务可按 profile 收紧 |
| 模型预算 | 必须配置调用/token 上限；模型未返回 usage 时标记未知并使用调用上限兜底 |
| 清理 | 正常步骤停止后保留独立、有限的清理窗口并记录异常 |

正式运行总预算包含计划相关模型调用、安装、原始运行、修复、验证、复跑；不存在“验收或 pip 安装自动加时”。

向模型服务发送请求时必须设置剩余时间约束；超时停止等待与后续调用不代表上游一定停止计费，应在费用说明中披露。

### 8.4 验证器信任边界

- 验证器不放在 Agent 可修改的工作目录；独立进程/容器执行，使用受信镜像。
- 从当前仓库复制回 `check.py` 再运行，只能保护该文件内容，不能防止仓库模块劫持、运行时依赖改变或产物伪造；不能据此宣称验证已独立。
- 验证器通过只读、限大小的数据通道读取声明产物，不导入修复后的仓库模块。
- 验证器固定阈值、计算方式、参考数据和随机性约定；这些不属于模型修复范围。
- 修复后的程序仍是不可信程序，独立验证只对已定义任务成立；无法据此证明所有数据来源和科研操作真实。
- 对需要执行仓库特定 Python 才能评价的任务，先设计可隔离的输出协议；做不到就不纳入首批 target 级任务。

### 8.5 失败路由

| 原因 | 处理 |
| --- | --- |
| 可修复依赖/代码错误 | 保留现有自愈机制，重跑失败执行阶段后重新验收 |
| 产物结构错误 | 提供结构差异给模型，只能修生产代码，不能改 schema |
| 指标不达标 | 仅受维护 profile 明确允许、且修复预算足够时进入有限修复；默认不进行无边界调参 |
| 缺私有数据/需要 GPU | 条件不足或当前不支持，结束并说明可补条件 |
| 预检信息不足 | 运行前补充或显式探索试跑，不占用执行 worker 等用户 |
| 安全规则拒绝 | 按拒绝语义记录，不放宽规则自救 |
| 预算耗尽/用户取消 | 结束并清理，保留已有证据 |
| 验证器故障 | 系统验收错误，不归类为仓库代码失败，不伪造结论 |
| 干净复跑失败 | 单独呈现复跑失败，不自动重新开启修复 |

### 8.6 干净复跑算法

1. 冻结原始 revision、有效计划、验证器、数据与修复材料。
2. 创建新的工作目录和新的沙箱会话；不得复用之前容器的可写层、已安装环境或输出目录。
3. 还原原始代码，应用经过路径校验的允许变更；包含新增文件和删除文件，而不只是普通 `git diff` 能看到的部分。
4. 还原声明的依赖和允许环境变量，使用相同数据版本；所有网络访问仍受部署策略约束。
5. 清空预期产物位置，运行同一命令，执行同一可信验证器。
6. 记录通过、失败或条件不足，并生成差异摘要；最终清理新会话。

v0.2 不承诺完全离线、位级一致的科学复现：镜像 digest、依赖版本/可取得的包哈希及数据哈希必须记录；无法固定的外部输入必须显式列为限制。

对于首批正式任务，应优先使用已有 CPU wheel 和小型公开/合成数据，避免把源码编译与大数据下载当成默认能力。

## 9. API 与事件契约草案

本节是拟议增量，不是当前已经提供的端点；现有创建、查询、取消、产物 API 优先扩展，不另建同义接口。

### 9.1 预检

| 接口 | 语义 | 关键字段 |
| --- | --- | --- |
| `POST /api/preflights` | 创建受限静态预检，202 返回 | repo_url、revision、profile_id、可选用户输入 |
| `GET /api/preflights/{id}` | 查询任务状态与检查结果 | status、resolved_revision、checks、plan、blockers、expires_at、confirmation_digest |
| `POST /api/preflights/{id}/cancel` | 取消预检及关联克隆进程 | 取消状态与清理结果 |

预检队列有部署级并发/长度上限；单用户首版可以复用现有 worker 管理模式，不引入 Redis/Celery。

创建响应里 `status` 是 queued/running/completed/failed/cancelled；完成结果另有 ready/needs_input/unsupported/unknown，避免混淆“检查完成”与“可以运行”。

### 9.2 正式运行

扩展现有创建请求：

- `preflight_id`、`confirmation_digest`：经用户确认的预检结果。
- `mode`：`formal / exploratory`；与预检冻结值一致，无预检只允许显式 exploratory。
- `acknowledged_unknowns`：用户在探索试跑中已确认的未知条件 ID；不能包含安全拒绝项。
- `verification_profile_id`：受维护任务或已确认的用户标准。
- `total_budget_seconds`：总预算。
- `require_clean_replay`：正式验证任务默认 true；探索试跑可 false。
- `parent_run_id`：补充条件后新建任务的关联。
- `Idempotency-Key` 请求头：重试不重复执行，相同 key 不同请求体返回冲突。

原有直接创建入口只代表显式的探索试跑，不得在没有完整确认和 profile 的情况下获得正式验证标签；前端正常路径统一走预检确认。

运行结果增加 `verification`、`replay`、`bundle`、`effective_plan_digest`、`code_under_test`、`budget_usage`、`evidence` 和 `limitations`；状态响应增加 `finalized`，用于判断所有收尾记录是否已完成。

现有 `verified` 字段仅表示当前环境是否达到本次声明的验证目标，必须由 `verification.status` 推导；不能用它代表干净复跑或整篇论文复现。要求复跑的任务只有当前验收与复跑均通过才进入 succeeded；复跑失败进入 failed，结果仍保留当前验收 passed 供解释。

新增只读能力：

- `GET /api/runs/{run_id}/verification`：结构化验收结果。
- `GET /api/runs/{run_id}/bundle`：下载已完成校验、已脱敏的复跑材料。

错误以稳定业务 code 区分：`preflight_expired`、`confirmation_mismatch`、`unsupported_runtime`、`verification_not_ready`、`bundle_not_ready` 等；不要把所有 404 都翻译成任务不存在。

### 9.3 事件

沿用现有有序事件序号，增加 kind，不更换传输协议：

- `preflight_check`、`plan_confirmed`
- `verification_started`、`verification_check`、`verification_finished`
- `replay_started`、`replay_finished`
- `budget_exhausted`、`bundle_ready`

事件 data 保存稳定的检查 ID、状态、证据引用、阶段归属；用户可读 message 不是前端提取指标的唯一来源。

预检检查保存在预检结果中；正式运行的 `preflight_check` 仅表示冻结快照里的相关事实，不隐含新增预检 SSE 或事件查询接口。

`final` 必须在结果、材料状态和清理结果落盘后发出，随后设置 `finalized=true`；查询返回最终事件序号。前端只在终态、结果可读、finalized 为 true 且事件游标达到该序号时停止刷新，不能仅凭当时的 last_event_sequence 误以为不会再有清理事件。

结果通过但清理失败，保留验收结论并单独警告；不能把残留问题藏在绿色状态后面。

收尾操作必须幂等：先持久化待收尾记录，再写结果/材料/清理状态，按固定标识写一次 final 事件，最后原子写入 finalized 与最终事件序号；同一运行不得生成多个互相矛盾的 final。

启动恢复处理两类中断：若结果与 final 已落盘但标记未写，核验它们后补齐 finalized；若运行或收尾尚未完成，则按服务中断结束，保留已验证证据、将未知复跑标记为 blocked，并仅清理该任务可识别的残留资源后完成收尾。这是失败恢复，不是自动继续执行或恢复训练。

最终事件序号一旦冻结，后续维护性清理不能向该运行继续追加会影响前端结论的事件；额外维护结果写单独的运维记录。恢复逻辑对截断 JSONL 尾部和重复启动有测试，不能靠查询时盲目补一个成功标记。

旧记录没有 finalized 时，只能按历史完整性提示读取，不能伪造新的收尾事件；历史终态页面按历史记录模式展示，不进入等待 finalized 的无限轮询。

### 9.4 存储

继续以 run 目录保存材料，新增内容建议包括：

```text
run_plan.json
preflight.json
verification.json
repair_manifest.json
replay_result.json
finalization.json
environment.json
patch.diff
report.md
result.json
reproduce.zip
```

预检使用独立记录区并有过期清理；运行记录只引用已冻结的预检快照，不依赖一个会被删除的临时目录。

增加 schema_version，读取旧记录时如实显示未采集的验证数据，不补造结果；这是历史数据读取需求，不要求把旧运行升级成正式验证。

## 10. 安全、隐私与材料导出

### 10.1 不可信仓库

仓库 README、代码、注释和模型输出全部是不可信输入，不能据此改变工具权限、网络策略、预算或验收标准。

公开服务上线前必须另做安全评审；本版本仍是本地单用户模式，不能因为使用 Docker 就宣称完全安全。

### 10.2 网络与文件边界

- URL 校验不仅检查 https：还要拒绝凭据、内网/回环/链路本地地址和危险重定向；域名解析与实际连接的防护需要一致。
- 仓库来源与依赖源分别限制；Git 下载、包下载和模型 API 不是同一种网络能力。
- 禁止宿主 Docker socket 和非任务目录挂载；资源限制继续由沙箱强制。
- 依赖安装能够执行包构建代码，字符串校验不能替代沙箱和网络隔离。
- 预检不递归读取软链接、不解析任意外部实体、不执行项目 hooks 或自定义 Git helper。
- 新旧路径都执行同一越界检查，覆盖 Windows 盘符、中文路径、软链接与容器路径表示。

### 10.3 导出要求

- 只允许导出清单声明的相对路径，拒绝绝对路径、`..`、软链接目标逃逸和重复冲突条目。
- 限制文件数、单文件/总大小，过滤 `.env`、凭据、模型密钥、宿主路径和未授权数据集。
- 不默认打包整个 workspace，也不重新分发不允许再分发的代码、数据或依赖。
- 优先交付原始 commit 引用、允许补丁/新增文件、依赖说明、数据获取说明、验收规则引用与结果；没有合法可导出的验证器时给出限制。
- 包含新的文件变更并不意味着把所有 untracked 文件都打进去；必须有明确允许范围和内容检查。
- 只有 `bundle.integrity=complete` 且压缩包写入完成，才能发出 bundle_ready；材料不完整时保留报告和可安全查看的证据，`GET /bundle` 返回 `bundle_incomplete` 或 `bundle_blocked`，UI 显示缺项，不提供误导性的完整材料下载。
- 冻结清单不完整时，不得利用旧目录里的隐含文件完成“干净复跑”；应将 replay 标为 blocked。若只是打包服务失败，而冻结清单已用于独立复跑通过，则保留复跑通过事实，但明确材料尚未交付。
- 导出材料附带哈希清单；哈希证明内容一致，不证明科学结论正确。

## 11. 前端实现建议

### 11.1 复用现有结构

- 在现有选择/引导流程内增加预检状态和确认卡，不再增加第二个功能相同的首页。
- 运行组件保留真实事件驱动，新增验证、复跑节点及对应详情。
- 报告组件负责摘要和文件预览，验证数据从结构化字段获取，不从 report 文本反向猜测。
- 将业务状态推导集中在当前模型/状态转换位置，避免页面、拓扑和抽屉各维护一套判定。
- 本轮不以换图形库、换 CSS 框架、增加复杂动效作为交付目标。

### 11.2 必须覆盖的交互

- 回车提交、Tab 顺序、折叠内容不可聚焦、弹窗焦点恢复、原生 summary 可操作。
- 预检取消、过期后重检、修改计划后重新确认。
- 刷新运行页后恢复任务；非法深链有明确回退。
- 断网重连、取消中的反馈、重复点击不重复任务。
- 报告未生成、部分证据缺失、快速切换运行/页签时不串数据。
- 运行时自适应笔记本宽度；失败说明不得只有悬浮提示才能看到。

### 11.3 新手启动体验

先交付宿主健康检查：Python、Docker 引擎、所需镜像和模型配置是否齐全；只返回脱敏状态，不在页面显示密钥。

扩展现有 `GET /api/health?details=true` 返回 `checks`，每项包含稳定 ID、`available / missing / unsupported / not_checked`、说明及下一步；默认 `/api/health` 保持进程存活探针语义，不能因 API 可访问就断言 Docker 已就绪。

页面根据检查结果引导启动；模型配置齐全不等于网关已连通，更不等于推理成功，未做连接检查时明确 not_checked。健康检查不自动发起付费推理请求，不回显模型密钥、代理凭据或宿主绝对路径。

M1 必须实际验证干净环境下的最短安装/启动步骤，以及缺 Docker、缺镜像、缺模型配置时的用户提示；不必为“一条命令”牺牲透明性，也不能静默安装 Docker、改宿主权限或覆盖用户配置。

## 12. 开发拆分与依赖

M0–M4 保留为完整 v0.2 的逻辑里程碑，不是本轮必须全部完成的顺序排期。8.5 天冲刺从中选取小型纵向闭环，实际范围、逐日依赖与降级门槛见第 12.1–12.7 节；不以全量 M4 作为预览版交付前置条件。

### M0：基线和契约，后续工作的前置条件

- 确认当前未提交 guidance/运行页改动与开放 PR 的整合策略，避免两套 UI 相互覆盖。
- 冻结结果语义、预检确认、预算和任务配置字段。
- 先做 3 个小型垂直案例：原样通过、依赖修复通过、缺条件明确结束。
- 记录当前版本在这些案例上的真实结果，不把内置演示数据算作验证成绩。

出口：接口草案评审通过，三例人工基准完成，已有行为回归测试可运行。

### M1：体检—确认—运行的易用性闭环

- 扩展当前 guidance 与输入校验。
- 实现异步受限预检、固定 commit、条件证据和过期处理。
- 实现确认摘要、幂等创建、明确总预算、运行结束后补资料重试。
- 实现 R12 的详细健康检查和启动引导，验证缺 Docker、镜像和模型配置的诊断路径。
- 前端接入预检卡、确认卡、明确运行进度；补齐预检变更/过期重建、排队后过期和重复提交的验收。
- 实现终态幂等收尾与启动恢复，不让异常中断的任务永远处于未 finalized 状态。

出口：新用户按文档从干净环境完成首次启动与真实试跑；缺组件有明确提示，条件不足任务不进入无意义修复；仍明确标为试跑而非指标复现。

### M2：可信验证与专业结论

- 扩展 target manifest，加入产物结构与受维护指标规则。
- 实现隔离验证器和 VerificationResult。
- 对接验证失败路由、证据展示和结果等级文案。
- 加入改阈值/改验收脚本/伪造日志/陈旧产物等负例。

出口：未达到标准的任务不能因退出码 0 或模型宣称成功而通过。

### M3：干净复跑与材料交付

- 建立完整 RepairManifest，处理新增/删除/二进制文件、必要忽略文件、依赖与允许环境变量，明确不完整时的拒绝语义。
- 新会话复跑、验证规则一致性、剩余预算检查；复跑与下载使用同一冻结清单。
- 生成限量、脱敏、路径安全的复跑材料，覆盖超限截断和材料生成失败，完整性未通过不发 bundle_ready。
- 报告展示同环境结果和干净复跑结果的差异。

出口：受支持任务可仅凭冻结输入和声明变更在新环境完成同一验证；缺外部条件时诚实显示限制。

### M4：评测与公开演示准备

- 扩展至 20 个冻结任务，完善对照实验与原始结果记录。
- 浏览器实测新手流程、键盘、断网、取消、刷新与跨运行切换。
- 更新使用说明和已支持范围，准备成功、修复、条件不足三个真实演示。

出口：满足第 14 节门槛，或明确保留为实验版本并公布未通过项。

建议 PR 粒度按“契约 → 后端实现与测试 → 前端与浏览器验证”组织；只有纯独立模块适合并行，不能让两个 PR 各自定义成功语义。

按现有[协作约定](../../interface-contract.md#L251)，contracts/run.py、sandbox/base.py 和接口契约需要两人 review，跨目录需负责人 review，超过 300 行的 PR 先拆分；本文仅提出后续契约变更，不直接修改这些既有规则。

### 12.1 八天半冲刺的前提与交付定位

排期更新日期：2026-11-21。用户已明确总期限为 **8.5 天，代码由 AI 编写**；此前“前后端两名开发、8 周加缓冲”的估算不再适用。本节替代旧排期，不把完整 v0.2 的所有 P0 等比例压进 8.5 天。

| D6 | 集成剩余支持案例及完整材料下载，打通总预算、复跑取消与终态；按门槛撤下不可靠入口 | 浏览器走完整流程，修复数据不同步、报告切换、键盘与错误态；整理操作说明 | **D6 末功能冻结**：明确本轮哪些任务/能力过关，哪些延期；其后不扩任务类型和功能范围 |
| D7 | 固定候选版本，真实 Docker 跑三例和负例；检查新环境重复结果、Windows/中文路径、材料还原 | 浏览器回归刷新、断网重连、快速重复提交、取消、历史结果；独立检查代码与证据 | 输出逐项通过/失败/未执行清单；阻塞问题优先修，不拿构建通过代替实际验证 |
| D8 | 只修阻塞并复测受影响链路；从干净环境按说明启动；完成可获得的新手试用和演示预演 | 核对结果边界、材料内容、截图与真实事件一致；整理已知限制和后续工作 | 固定可演示版本、成功/修复/缺条件三条真实路径；有遗留阻塞则明确降低交付等级 |
| 最后 0.5 天 | 封版检查、保留代码基线与证据、交付支持清单和操作步骤 | 最短黄金路径复测；整理后续缺口 | 不新增功能、不自动部署；交付真实可运行版本或诚实标注缺口的体验预览版 |

D2、D4、D6 是三次可操作检查点，不是三次自动发布。每一天都联调测试，最后 2.5 天用于集中验收而不是第一次运行代码；AI 编码提前完成的容量优先补回归，不加需求。

### 12.4 AI 分工与关键路径

| 工作流 | 独占或主责范围 | 输入与交付 | 不得自行处理的事项 |
| --- | --- | --- | --- |
| A：核心集成 | 契约、API、runner、状态/预算、清单与复跑调度 | 冻结的接口与判据；交付可运行 API、阶段测试和集成结果 | 不覆盖用户未提交工作，不未经授权合并 PR |
| B：前端体验 | 四视图、事件展示、交互、浏览器回归 | A 的契约和真实响应；交付可操作页面及实测记录 | 不新增另一套成功语义，不用假数据作为验收证据 |
| C：验证器与测试 | 独立规则、数据格式、安全读取、负例和案例证据 | 固定任务说明/阈值；交付隔离验证器与可重复测试 | 不与 A 同时自由修改 runner/契约，不降低指标换取通过 |

- 三路应使用文件所有权或隔离分支/工作树；共同字段只由 A 统一集成，前端和验证侧提出变更请求，不能各自先改一套。
- D1 就冻结“预检/确认 → 运行 → 证据 → 材料 → 复跑”的最小数据契约；D2 开始记录修复材料，不能 D5 才从旧容器猜安装过什么。
- 验证器模块及负例在契约冻结后即可独立开发，不必等待所有生命周期加固完成；真实集成按依赖验收，不把模块单测算成全链路完成。
- 关键路径为：固定任务与输入 → 产物协议/可信判据 → 真实运行与独立验收 → 声明变更还原 → 新环境同规则复验。页面布局可并行，阶段出口不能跳过。
- 不为本轮临时建设 Agent 调度平台。AI 自审不是独立验收，也不自动满足既有“两人 review”要求；必要 review 资源缺失时，相应变更不能标记已满足合入要求。

### 12.5 本轮验收规模与证据要求

本轮是功能与可信性验收，不是产品优越性实验；第 14.2–14.5 节的完整研究型评测延期。

1. **3 个垂直案例**：原样通过、修复后通过、缺条件明确结束；在 D1–D2 核实可行性并冻结，优先覆盖现有两个真实库的小任务。缺条件案例的正确结果是 blocked/unrepairable 等明确终态，不要求它复跑成功。
2. **至少一个真实目标验证闭环**：固定规则检查实际数值产物，报告任务/数据/指标来源；不从模型摘要或任意日志里直接提取“成功”。测试用例自身 PASS 不自动等于用户任务达到 target。
3. **重复性**：候选版本上，两个可完成案例各做 2 次独立端到端执行，每次含一次干净复跑；缺条件案例至少确认一次正确终态。修复后更换候选版本需重测受影响用例，并保留旧失败记录，不择优覆盖。
4. **必测负例**：退出 0 但无本轮产物、陈旧产物、指标不达标但日志报喜、尝试改验证器/阈值、同名模块劫持、清单缺依赖/文件、截断/越界/敏感文件，以及已开放阶段的取消、超时、崩溃收尾。规则可缩窄，实际暴露的边界不可跳测。
5. **浏览器与启动**：支持的平台实际启动，走四视图黄金路径和断网/刷新/重复提交/取消/报告切换；若能安排，邀请 1–2 位未参与开发者试用并记录是否需要帮助。未安排到就写“未进行新手试用”，不能称已达到 5 人门槛。
6. **证据交付**：固定代码/任务/模型标识、实际执行的源码或包版本、运行/复跑 ID、判据版本、数值结果、材料完整性、失败记录、已知限制。没有实际跑到的测试标未执行，不填通过。

上述目标尚未执行，不默认模型额度已授权。真实模型调用先估算小样本成本并确认可用预算；缺额度可做确定性集成测试，但必须披露尚未完成真实模型修复验收。

完整对照为 20 任务 × 3 组 × 3 次 = 180 次试验，每次若占满 900 秒，串行执行本体约 45 小时，另有准备与异常处理；不能因代码由 AI 写就当作这部分不耗时。本轮不接入新的通用 Agent 以追赶这一指标，不宣称已证明优于通用 Agent。现有队列长度 5 也不代表 5 路执行并发。

### 12.6 截止检查与降级规则

| 截止点 | 必须检查 | 不通过时的处理 |
| --- | --- | --- |
| D1 前半天 | 接口、基线与任务范围是否可拆单，是否有既有代码冲突 | 先用一个已知任务贯通，暂缓自定义入口/复杂页面；不能覆盖未提交工作或跳过必要 review |
| D2 末 | 首个任务能否从真实页面确认后执行、展示结果 | D3 优先修这条链，减少体检字段和视觉效果；不并行扩任务数掩盖闭环失败 |
| D3 末 | 已开放阶段的剩余预算、取消清理、幂等和中断收尾是否可靠 | 先修生命周期；有已知失控执行路径则暂停该入口，不靠降结果标签掩盖，不能拖到最后半天 |
| D4 末 | 独立验证是否真实隔离，负例能否被拒，至少一个指标是否有来源和实测证据 | 未通过的规则不授予 target；artifact 也必须有结构与本轮来源检查，否则只能 execution；将专业验证目标记未完成，不降阈值 |
| D5 末 | 声明变更能否在新目录/新容器还原，验证是否一致 | D6 仅集中修复这一关键路径；不支持的变更类型明确拒绝/标不完整，不复用旧容器假复跑 |
| D6 末 | 可交付入口是否完整、可取消、能终止；验证/复跑/材料是否有真实证据 | 冻结已通过范围；复跑/材料仍不可靠则停止开放相应能力，交付降为体验预览版，R07/R08 保持未完成 |
| D8 与最后半天 | 安全/假成功负例、真实浏览器、清理和候选版本回归是否通过 | 不交付存在已知安全绕过或假成功的入口；无法修复则明确标记该入口不交付，不用展示录像替代功能完成 |

可裁的是通用程度、任务数量、动效和新增入口，不可裁的是已开放能力的安全、结果真实性和证据。未要求复跑的探索任务仍可显示“试跑通过，未验证可复跑性”；原本要求复跑但失败的正式任务不得偷偷改成探索成功。

### 12.7 每日沟通与最终交付

每日用四项沟通：今天能实际点通什么、哪些验收通过/未通过、当前唯一关键阻塞、明天是否需要按第 12.6 节缩范围。重点一起看 D2 页面闭环、D4 指标证据、D6 复跑与范围冻结，不按 AI 生成了多少文件评进度。

最后交付清单：

- 可本地启动的预览版本、明确支持的任务/环境和最短操作步骤。
- 四视图真实流程，成功、修复、条件不足三条案例及限制说明；未完成案例如实列出。
- 已通过规则的指标证据、干净复跑记录和完整性通过的材料；未完成能力不展示成功徽标。
- 候选版本回归清单、失败/未执行记录、已知缺陷及完整 v0.2 的延期需求。

本轮目标是用 8.5 天交付“小范围但从头到尾真实可用”的版本，不是完成整个科研复现平台。业务实现需后续明确开工，发布/合并/付费完整评测仍分别按授权执行。

## 14. 测试与量化验收

本节保留完整 v0.2 的测试设计和价值验证协议，不在 8.5 天内全部执行。本轮按第 12.5 节的小样本范围、第 12.6 节交付门槛验收；下表中实际开放能力涉及的安全与假成功负例仍必测，未开放能力标记未实现，不冒充测试通过。第 14.2–14.5 节的大规模对照及正式版门槛延期，不以本轮演示替代。

### 14.1 自动化验收矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| 原仓库直接通过 | 不制造修复记录；结果显示实际验证等级 |
| 安装失败后修复 | 重跑安装，再运行与验证，不跳过前置条件 |
| 缺私有数据/需要 GPU | 明确条件不足或不支持，不无限修改代码 |
| 命令退出 0、没有本轮产物 | artifact 验证失败 |
| 预留一个旧产物 | 不能作为本轮成功证据 |
| 指标未达标、日志写“成功” | target 验证失败 |
| 模型修改阈值或验证脚本 | 修改被拒，或独立验证不受其影响 |
| 仓库模块同名劫持验证依赖 | 独立验证器不导入仓库模块 |
| 修复新增必要文件 | 复跑材料完整，新环境可使用该文件 |
| 必要二进制/被忽略文件/删除操作 | 清单准确还原；安全或许可条件不允许时明确 incomplete/blocked |
| 补丁或文件超限被截断 | 不发 bundle_ready，不宣称完整材料；报告明确缺项和影响 |
| 复跑清单与材料包哈希不一致 | 拒绝材料完整性验收，不能只以某一次复跑通过掩盖交付缺项 |
| 只在旧容器手工安装了依赖 | 清单必须记录；记录不全则干净复跑不能假通过 |
| 中文宿主路径、Windows Docker | 路径/编码检查不误报，验证真实挂载而非字符串想当然相等 |
| 预检/LLM/安装/复跑超时 | 正确阶段结束，预算不被抬高，进程/容器有清理记录 |
| 用户在复跑阶段取消 | 不再创建后续步骤，当前会话清理，状态与日志一致 |
| 预检后修改参数/commit | 必须新建预检和确认摘要，旧记录保持不变 |
| 预检受理前过期、受理后排队过期 | 前者要求重检；后者使用已冻结快照，不偷偷跟随最新分支 |
| API 创建重试 | 同一幂等键仅创建一个运行 |
| final 写入后、finalized 写入前进程退出 | 重启幂等补齐标记，最终序号一致，无重复 final、无无限轮询 |
| 运行中断/事件尾部截断/反复重启 | 以服务中断收敛，保留证据，不恢复执行、不补造成功 |
| 缺 Docker、镜像、模型配置 | 健康检查逐项说明，普通用户可按建议处理，不回显密钥 |
| 前端断网、刷新、切换报告 | 恢复后不漏事件、不串报告、不伪造进展 |
| 包含敏感文件、越界路径的导出 | 禁止进入材料包；错误可解释 |

没有 Docker 的测试环境可以跳过真实容器用例，但发布验收必须在支持的平台实际运行，不能以 skip 代替通过。

### 14.2 20 个任务如何选

建议任务组成：

- 6 个原样可运行的任务。
- 8 个允许范围内可修复的任务，覆盖依赖和代码问题。
- 4 个明确条件不足或当前不支持的任务。
- 2 个会执行但提供不合格产物/指标的固定验收负例，关闭自动修复，只检验能否拒绝假成功，不计入可完成任务的成功率分母。

至少来自 10 个不同的上游仓库，固定 commit 和输入；这叫“20 个任务”，不冒称“20 个独立仓库”。

自然失败与人为故障注入分开统计，注入原因、补丁和预期结果公开；内置靶场不能充当全部泛化证据。

至少 5 个任务在实现期间不用于调整提示词/规则，作为留出集；维护者先做人工基准，确认任务在规定资源下确实可验收。

### 14.3 对照组

| 组别 | 设置 | 目的 |
| --- | --- | --- |
| A | 当前 Harness 基线 | 判断升级是否真实改善已有产品 |
| B | mini-swe-agent 等通用 Agent，固定版本 | 回答“直接使用现成 Agent 是否已经足够” |
| C | 升级后的工作台 | 测量预检、专业验收和干净复跑的收益 |

三组尽量使用同一模型与版本、输入说明、CPU/内存、数据、时间/token 预算和网络可达条件；工具能力不同必须披露，不能故意给 B 较差环境。

通用 Agent 原生 shell 不等于我们的 ACI，不能声称无损接入或完全同配置；将其放在独立受限评测环境，结束后由统一外部验证器判分。

三组都接受同一份任务说明与交付要求，都由相同版本的外部验证器检查当前环境结果，并且都执行一次同配方的干净复跑；不能只检查 C 的复跑，也不能把 B 口头宣称成功当成验收通过。评测器只能格式化各组已声明材料，不能偷偷补齐某组没有记录的文件或依赖。

在完整评测前冻结分段预算，例如每次试验执行/修复阶段 600 秒、验收与复跑阶段 300 秒，总共 900 秒，各组相同；C 使用评测器提供的同一复跑阶段，不额外获得时间，也不重复做第二次计分复跑。任务允许更小预算，但必须对三组一致且事先固定。

记录两套开销：产品端到端时间/模型调用（包括 C 的预检）与统一外部评测开销；最终总时间也要给出。预检若使用模型，其调用计入同一模型额度，不能作为免费信息优势；评测器本身不调用模型评分。

在获批的完整评测中，每组每个任务独立重复 3 次；14 个可完成任务产生 42 个计分试验，条件不足和固定验收负例单独计分。留出集、自然失败和注入故障分别报告，不只展示合并均值。

真实 API 调用有费用；先做 3 个非留出任务的小样本估算，冻结实验协议并得到预算确认后再跑完整对照，不自动启动大量付费评测。

### 14.4 指标口径

- **主要指标：完整可复跑交付率**：在 14 个可完成任务的 42 次试验中，当前验收、统一干净复跑、材料完整性全部通过的比例；分母固定，不排除超时、工具崩溃或模型拒绝。
- **验收通过率**：在人工确认可完成的任务上，达到该任务规定等级的比例；不能拿 execution 通过冒充 target 通过。
- **干净复跑通过率**：当前环境已通过且要求复跑的任务中，新环境同规则通过的比例，同时报告分子/分母；这是条件比例，不能替代上述固定分母的主要指标。
- **验证等级误报数**：界面宣称达到某等级，但统一外部验证器未通过的次数，包括篡改验收和陈旧产物。
- **完整成功误报数**：界面宣称全流程可复跑成功，但要求的复跑或材料完整性未通过的次数；如实报告“target 通过、复跑 blocked”不算误报。
- **条件不足识别**：分别报告准确率、漏报与把可完成任务误拒绝的数量。
- **时间**：预检与运行分别记录，运行包含修复、验证、复跑；报告中位数与长尾。
- **模型开销**：调用数、可取得的输入/输出 token、按记录的价格表估算费用；缺 usage 时不报精确金额。
- **上手成本**：用户完成任务所需人工操作、首次成功时间、寻求帮助次数。

### 14.5 建议发布门槛

以下是待验证的目标，不是当前成绩，也不是预先承诺一定超过通用 Agent：

1. 全部安全与假成功负例通过，20 个任务中没有观测到误报成功；明确这不是“误报概率为零”的统计证明。
2. 3 个垂直演示任务在新环境连续完成 3 次，结果等级和证据一致。
3. 至少 5 位未参与开发的试用者中，4 位无需口头指导即可完成首个受支持任务；首次运行交互不要求手写 shell 命令。
4. 所有失败都有阶段、稳定类别、证据和下一步；下载材料不含密钥或不允许导出的数据。
5. 预先把“完整可复跑交付率”定为主要收益指标：在相同预算下，C 比 B 至少高 10 个百分点，即 42 次计分试验至少多 5 次完整交付；同时披露 A 组对照、逐任务结果、时间与成本，不在看到结果后改挑另一项有利指标。

主要指标和门槛可以在小样本试验后、运行留出集及完整对照之前调整，但必须留下新协议版本和理由，不能事后挑结果。20 个任务提供的是小样本价值证据，不证明对所有科研仓库有泛化优势。

若第 5 项未达到，产品仍可按实验版本展示真实结果，但不能宣布已证明优于通用 Agent；优先调整范围或收缩成科研验收工具，不通过新增页面或增加 Agent 数量掩盖问题。

## 16. 主要风险与建议取舍

| 风险 | 建议处理 |
| --- | --- |
| 维护任务配置和验证器需要科研知识 | 首批任务宁少勿泛，每个指标说明来源与边界 |
| 指标调参比修依赖昂贵 | 首版只对明确允许的任务做有限修复，不承诺自动研究 |
| 干净复跑增加时间和费用 | 确认页明确告知；探索试跑可选择不复跑，但不授予正式可复跑结论 |
| 依赖/数据下载不稳定 | 固定输入并记录可取得哈希，基础设施失败与代码失败分开 |
| 无法保护所有科研语义 | 限定验证器能证明什么，不承诺彻底杜绝科研造假 |
| 现有分支和 PR 同时修改运行页 | 先处理基线整合，再分工，禁止直接覆盖未提交代码 |
| 模型能力变化导致结论失效 | 评测冻结模型标识、参数、日期和任务版本，保留原始结果 |
| 工作台价值不明显 | 用真实对照决定是否继续做平台，必要时改成验收插件 |
