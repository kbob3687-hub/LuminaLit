# 前端设计规范（Taste Skill + Impeccable 落地版）

- 日期：2026-11-17
- 状态：**待与队长确认**（视觉定调属于两人共识项）
- 依据：队长要求「前端别做成一股 AI 味或古老管理系统，要有冲击感」
- 适用：`PaperHarness / LuminaLit` 前端（React + TypeScript + Tailwind）

> 这份文档把两套外部设计 Skill 的共同内核抽出来，落成本项目可执行的规则。

## 2. 本项目采用的核心规则

### 2.1 三旋钮（决定整体气质）

Taste Skill 的三个参数，我们这样取值：

| 旋钮 | 取值 | 理由 |
|---|---|---|
| `DESIGN_VARIANCE`（布局方差） | **中高** | 三视图如果都是对称居中大卡片，就是典型 SaaS 模板。进度页用非对称分栏（左日志流 / 右补丁 diff），信息密度本身就有视觉张力 |
| `MOTION_INTENSITY`（动效强度） | **低到中** | 这是**工具型产品**，不是官网。候选人要看清"上一步做了什么"，动效过多会干扰判读。动效只用在**状态跃迁**（queued→testing→repairing→succeeded）和**终态反馈** |
| `VISUAL_DENSITY`（信息密度） | **高** | 展示的是日志、diff、exit_code、failure_category。空荡的留白会让人怀疑"是不是没东西"。该密的地方要密 |

### 2.2 Impeccable 的 register 判定

它把设计任务分两类：

- **brand**：设计本身是产品（官网、落地页、作品集）
- **product**：设计服务于产品（应用 UI、后台、工具）

**我们是 product。** 这条判定很关键——它意味着：

> 前端的目标不是"让人哇"，而是"让人三秒看懂现在跑到哪一步、为什么失败"。
>
> 视觉冲击感来自**运行过程本身的呈现**（实时日志流动、diff 高亮、状态跃迁），不是来自装饰性光斑。

### 2.3 绝对禁令（照抄，一条不留）

这些是两套 Skill 的共同底线，本项目一律禁止：

| 禁令 | 为什么 |
|---|---|
| 左侧彩色竖条（`border-left > 1px` 当强调） | 最典型的"AI 生成感"标记 |
| 渐变文字（`background-clip: text`） | 装饰性，无信息价值 |
| 默认玻璃拟态（毛玻璃卡片） | 当前最饱和的 AI 模板特征 |
| Hero 大数字模板（大数字+小标签+辅助统计） | SaaS 陈词滥调 |
| 一模一样的卡片网格（同尺寸卡片无限重复） | 视觉 monotonous，也说明信息没分层 |
| 第一反应就用 Modal | 懒。先试行内展开 / 渐进披露 |
| 破折号 em dash（`—`）与 `--` | 中英文都禁，用逗号/冒号/分号/括号替代 |

### 2.4 四步色彩策略（选一个，别都选）

Impeccable 给的四个档位，从"克制"到"浸润"：

1. **Restrained**：中性色 + 一个强调色 ≤10% 表面
2. **Committed**：一个饱和色承担 30–60% 表面
3. **Full palette**：3–4 个命名角色色，各司其职
4. **Drenched**：整个表面就是这个颜色

**我们的选择：Restrained + 语义色例外。**

理由：这是工具型产品，主界面应当克制，让**状态色**成为唯一的高饱和元素：

| 语义 | 用途 | 注意 |
|---|---|---|
| 中性底色 | 页面背景、卡片 | **不要纯黑纯白**，朝品牌色偏一点（chroma 0.005–0.01） |
| 运行中 / 诊断中 | 状态点、进度条 | 一个冷色 |
| 修复中 | 状态点 | 与运行中区分（避免"都蓝"） |
| 成功 | 终态 | 绿，但别用刺眼的纯绿 |
| 失败 | 终态 + failure_category | 红，但**只在终态用**，否则满屏红噪声 |

`failure_category` 的展示要有明确色阶：`path_escape` / `replace_not_unique` 这类**校验类失败**和 `version_conflict` / `missing_dependency` 这类**环境类失败**应当视觉可分——这正是我们 ACI 层做的分类，前端要能把它讲出来。

### 2.5 主题：不用"默认深色"

Impeccable 要求先写一句**具体使用场景**，句子不够具体就重写。

我们的一句：

> 评委或队长，在答辩教室的投影仪上（环境光偏亮、对比度差），或者在深夜自己笔记本前，看一个跑了几分钟的复现任务**失败了**——他要立刻判断是环境问题还是我们的代码问题。

这句话的推论：

- 投影仪场景 → **对比度必须硬**，低饱和浅灰在投影上会糊成一片
- 失败场景 → **失败态的信息层级最重要**，不是成功态
- 因此：**浅色为默认**（投影友好），深色作为可选；两种都要保证失败态可读

> 这一条我标为「待定」——如果你或队长倾向深色（技术产品常见），我们可以反选，但理由必须换成具体的，比如"演示环境是昏暗教室 + 大屏"。

### 2.6 排版与布局

- 正文行宽 **65–75ch**，超了会散
- 层级用**字重 + 字号**双对比，相邻层级至少 **1.25 倍**差
- 间距要有节奏，不要所有 padding 都一个值
- **卡片是懒答案**，只在确实最合适时用；**嵌套卡片永远错**
- 不要什么都套容器

### 2.7 动效

- **不要动 CSS 布局属性**（width/height/top/left），用 transform / opacity
- 缓动用指数曲线（ease-out-quart / quint / expo），**不要 bounce / elastic**
- 我们的动效清单（只有这三个）：
  1. 状态跃迁时状态点的过渡
  2. 新日志行进入时的淡入（不是逐行打字机，太慢）
  3. 终态结果出现的整体呈现

## 3. AI 味自检（交付前必过）

Impeccable 的「AI slop test」，我改成两问，交付前对着问：

### 第一问：不看内容，只看气质

> 如果别人看一眼就说"这是 AI 做的吧"，那就是失败。

我们最容易踩的三处：

1. 三视图都是居中大卡片的对称布局
2. 用了光斑/粒子背景但没有信息意义
3. 状态色用了蓝紫渐变

### 第二问：类别反射检查

> 如果光看"这是论文复现工具"就能猜出配色和风格，说明落入了训练数据反射。

- **一阶反射**：科研工具 → 深蓝 + 等宽字体 + 终端绿
- **二阶反射**：不是深蓝 → 那就"编辑部风格衬线体 + 大留白"

两个都要避开。我们的答案：**用运行过程本身做视觉主体**——真实 diff 的增删行、真实日志的时间戳、真实的 exit_code。这些东西没有模板味，因为它们是数据。

## 4. 明确不采用的

| 不采用 | 原因 |
|---|---|
| 整套 Framer Motion 动画体系 | 工具型产品不需要，且增加包体积与调试成本 |
| Aceternity UI 的光斑/光束背景 | 正是"AI 味"最饱和的符号 |
| React Bits 的复杂文字动画（SplitText / DecryptText 等） | 演示时每次刷新都重播，干扰判读 |
| Uiverse 的装饰性按钮 | 单个零件可以借，但默认样式过于花哨 |
| Taste Skill 的 v2 experimental 规则 | 仍在迭代，措辞会变，不适合两天窗口 |
| Impeccable 的 23 个命令全流程 | 时间不够，只取「shared design laws」+「absolute bans」 |

**可以借的**：React Bits 的 `AnimatedList`（日志流）、`CountUp`（耗时/尝试次数）；Uiverse 的加载态。都只借一两个，不整套上。

---

## 5. 需要队长确认的三件事

1. **主题**：浅色默认（投影友好）还是深色默认？理由要具体到使用场景，不要"技术产品都用深色"。
2. **品牌色**：队长有没有指定？没有的话我按「深色中性 + 一个冷色强调」起。
3. **"冲击感"的定义**：队长说要有冲击感。我理解为「运行过程的实时呈现足够强」，但如果他指的是「首屏视觉足够炫」，方向会不一样，需要他一句话澄清。
